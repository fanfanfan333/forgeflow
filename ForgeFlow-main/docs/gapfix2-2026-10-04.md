## 2. 代码变更（4 文件，全部加性）

**`forgeflow/config.py::Settings.project_root`** / `::Settings.resolved_project_root`
新增 operator 声明字段（默认 `""` ⇒ 零行为变更）+ 访问器。字段注释显式说明「空 ⇒ 不注入，
项目类任务保持诚实 blocked，而不是被塞一个编造的路径」。

**`forgeflow/runtime/planning.py::PROJECT_REFERENCE_MARKERS`** / `::intent_references_project`
保守词表（`当前项目/本项目/代码库/仓库/项目架构/this project/current project/repository/codebase`）
与判定函数；模块 docstring 显式披露这是**唯一经用户授权**的意图关键词例外（裸 `code` 刻意不入表）。

**`forgeflow/runtime/orchestrator.py`**
- `::_resolve_inherited_resources`（新）：读父运行**真实** `declared_inputs["resources"]`，经
  `ResourceService.resolve_task_inputs` 重解引用；`parent_run_id` / `continued_from_run_id` 两键都认；
  无父/未知父/无资源/解析失败一律降级 `({}, [], "")`（资源接缝永不弄坏一次运行）。
- `::_capability_context`：新增两条旁路注入（继承资源→planner 输入；operator root→`repo_path`）。
  **关键安全属性**：注入写的是本地 `explicit`，既不经 `_resolve_resource_inputs`，也不回写
  `task.context` —— 因此 `_is_code_task` 不会被翻转（见 §5 实测）。
- `::_resolve_continued_context`：父键改为 `continued_from_run_id` **或** `parent_run_id`。
- `::_declared_inputs`：继承发生时补 `resources`（真实 id 去重合并）与
  `inherited_from_parent_run_id`（来源可追溯），"declared == planner 所见" 不变式不破。

**`forgeflow/runtime/react_executor.py::ReactExecutor._narrow_tools_for_declared_data`**（新，静态）
当运行带有**已声明的数据文件**（平台自身信号 `_is_analysis_task`：资源解引用出真实数据输入）且未声明
`table` 时，把 `data.query` 从模型可见工具集摘除，并把 `analysis.profile` 提到首位；有真实 `table`
声明（数据库资源）则保留 `data.query`；任何异常返回原集合（提示永不弄坏一次运行）。

## 7. 关键补充证据：Gap A 的 live 读回 / 差分 / 反事实

### 7.1 为什么需要补充

运行记录里**看不到** planner 的 `explicit_inputs` —— 注入是刻意的旁路，不回写 `task.context`，
所以「A 失败」既可能是「注入没生效」，也可能是「注入生效但模型没用」。两者必须分开。

### 7.2 手段

启动一台**仪表化后端**（`_run_backend_gap2b.py`），差异仅三点且全部披露：`reload=False`（让
启动进程**就是**服务进程，读回即服务进程自身的配置）、`AGENT_RUNTIME_MODE=deterministic`（ReAct 档
不向模型披露输入，无法用来判定；deterministic 与 react 共用 `orchestrator._capability_context`
这同一接缝，故是有效仪器）、显式 Selector 事件循环（本机 INC26 已知：裸 uvicorn 会拿到
ProactorEventLoop，psycopg 异步 checkpointer 会拒；项目自身靠 `--reload/--workers` 规避）。

### 7.3 服务进程自读回（`qa_tmp/_run_backend_gap2b.log`，PROJECT_ROOT 已配置）

## 8. 新发现（本次开出，均有上节证据）

### F-136（P1，平台侧）ReAct 不向模型披露平台已注入的输入

`react_executor.py::REACT_SYSTEM` 只给模型**工具名**；规则 6 仅披露「若任务带有平台已声明的本地数据
文件（其 `paths` 已由平台注入），要用 `analysis.profile`」。对 `repo_path`（以及 `table`）**没有对等披露**。
而 `ReactExecutor._effective_args` + `PLATFORM_OWNED_ARGS` 恰恰是在**模型选中工具之后**才把平台真实值填入 ——
即：**平台有值，模型不知情**。后果：项目/仓库类任务在 react 档下模型只能靠猜（实测 8B 从未尝试
`git.diff`/`code.lint`，而是枚举 document/sheet/pdf/textfile/data.query/analysis.profile 然后集体 blocked）。
这一处不对称是 A 失败的**平台侧**成因。（修复方向与规则 6 同构，属设计层改动，需用户裁定后再动。）

### F-137（P1，产品缺口）「分析当前项目的技术架构」在现工具目录下无成功路径

把 `repo_path` 变成真实可用后，能被它触发的路径只有 `code.run` / `code.lint`（`paths` 由 `repo_path` 满足）
与 `git.diff`（只给 diff，且要求工作区有变更）。实测在真实仓库上：`code.run` 因
**1031 > 500 文件上限**被拒 ⇒ 运行 outcome=failure。工具目录里没有能产出「项目架构总结」的工具。
顺带披露一个行为后果：**deterministic 档**下配置了 `project_root` 后，该类任务会由 partial 变为
failure（`code.run` 被拉起后失败）；生产默认（真 provider ⇒ react）不受影响，因为 `_is_code_task`
实测仍为 `False`。

### F-127 的残余

`data.query` 已被成功摘除（B 的计划里确实没有它），但 8B 也没有转向 `analysis.profile` ——
残余属**模型能力**（原报告即如此归类），平台侧能做的（收窄 + 提位）已做且已验。
