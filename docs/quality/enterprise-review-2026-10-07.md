# ForgeFlow 项目审查与升级记录

审查日期：2026-10-07。依据：当前工作区的实际实现和本次本地验证。原有未提交修改已保留；本次没有提交 Git、发布服务或修改线上系统。

## 判断

项目具有实际的多智能体参考工作流和较完整的治理模块，适合作为企业应用的工程基础。当前不能将整个产品认定为完成生产验收的、可水平扩展的企业级 Multi-agent 平台。

`forgeflow/graph/builder.py` 实际构建 Supervisor、Researcher、Analyzer、Executor 和人工审批节点，属于真实的多智能体图。通用工作区则主要由 `runtime/orchestrator.py`、`react_executor.py` 驱动工具调用；离线模式的步骤标注为 agent，不能据此证明独立智能体进行了协作。`support_ops` 和 `finance_recon` 仍是模板脚手架。

后台任务、实时事件及停止控制依赖当前 API 进程。数据库中的运行头记录可恢复历史，进程崩溃后的运行会标记为 interrupted，这与自动续执行、分布式任务接管是不同的能力。

## 文档能否上传、修复并返回

已有真实链路：资源上传 → 任务引用资源 ID → 文档工具写入新文件 → 校验 → 产物引用 → 下载接口 → 前端下载按钮。

本次新增测试通过实际 HTTP 上传 Word 文档、清空资源缓存、提交明确的文字替换操作、下载新 Word 文件，再重新打开文件核对修改内容。原始文件不被覆盖。这个测试使用内存存储和明确的编辑操作，不证明真实模型能处理任意自然语言需求，也不证明所有复杂文档可修复。

| 类型 | 当前实现 | 边界 |
|---|---|---|
| DOCX | 文本替换、段落和章节改写，生成可下载文件 | 复杂排版、严重损坏的 OOXML、视觉质量仍需专项验证 |
| PPTX | 文本、备注等声明支持的操作 | 不承诺任意母版、动画、图片或复杂形状编辑 |
| XLSX/XLSM | 单元格值、文本及显式公式操作 | 公式默认保护，复杂工作簿需要实际应用验收 |
| PDF | 读取、策略选择及重新生成 | 不承诺原文件上的任意内容和版式编辑 |
| 文本/代码文件 | 独立文本编辑平面 | 不等于 Office 文档修复 |

自然语言修改需要可用的真实模型和可执行的操作。未修改、能力缺失、校验失败应显示实际原因。`Makefile` 是开发检查和启动入口，不负责修复用户文档；项目内没有找到名为 makefire 的独立实现。

## 本次直接修复

| 问题 | 改动 | 验证方式 |
|---|---|---|
| 上传先整文件读入内存后检查大小 | 读取最多配置上限 + 1 字节，超限返回 413，关闭上传文件 | 超限读取次数及实际读取大小测试 |
| 上传后重启/另一工作进程无法解析缓存外资源 | 提交时按 ID 从存储加载资源，运行时独立快照 | 清空缓存后完整上传、修改、下载测试 |
| 共享资源索引和续聊引用缺少租户核实 | 两个任务入口校验资源和父任务所属租户；运行快照不回退到共享缓存 | 跨租户资源、父任务、并发快照测试 |
| 历史父任务不在最近 200 条中时无法续聊 | 按 ID 加载持久化运行头 | 清空运行和资源缓存后读取父任务测试 |
| 发送失败丢失已选附件和草稿 | 提交被接受后才清理附件；失败恢复草稿，保留请求期间新输入 | Chromium 中失败后重试，核对两次请求携带相同资源 |
| 前端仍提示“仅支持 DOCX 修改” | 从后端 `/documents/capabilities` 显示实际文档能力 | PPTX 能力提示的浏览器验证 |
| Windows 中文 Git 提交导致解码异常 | Git 输出显式按 UTF-8 解码 | 原有重复提交幂等测试恢复通过 |
| 同一技能并发演化可能越过幂等/冷却检查 | 单进程按租户和技能互斥，空闲锁自动释放 | 同技能串行、不同技能并行测试及原有演化回归 |
| 异步任务排队没有总容量上限 | 新增 `WORKSPACE_MAX_PENDING_RUNS`，默认 128，包含排队及执行中的任务；满载 503 + Retry-After | 并发提交只能接受一个任务和接口状态测试 |
| 部署默认多副本与进程内运行状态冲突 | Compose/Kubernetes/Helm 默认单 API 副本；Helm 关闭 API 自动扩容，Kubernetes API HPA 固定 1 | 静态部署配置检查，未部署集群 |
| 容器文件存储没有持久化挂载 | 上传与文档产物存储卷；Kubernetes/Helm PVC、可写临时目录与卷权限 | YAML 语法检查；卷挂载需目标集群验收 |
| 全栈本地检查入口不完整 | Makefile 新增 `check-full`、`test-document-delivery` | 后端检查、前端构建和 lint 分别执行 |

单实例部署使用 Recreate 更新，更新时存在服务中断。新存储卷不会自动迁移旧临时目录中的文件；已有部署升级前应备份并迁移上传和产物文件。Docker 镜像需重新构建以包含目录权限调整。持久化卷不能取代数据库备份，也不能使中断的任务自动继续执行。

## Skill 学习与沉淀

实际存在经验提取、去重、记忆分层、候选编译、critic/repair、版本治理、Golden 回归、发布审批、演化冷却和代际上限。这些模块比简单地保存提示词更完整。

默认技能测试仍以声明校验或受限模拟执行为主（`skills/tester.py`）。结构检查通过不等于技能在真实业务上有效。部分演化幂等状态是进程内账本；本次互斥解决单进程并发竞争，未实现跨进程锁。生产阶段需要把发布与演化操作放进数据库事务，并将实际任务效果、数据隔离、敏感信息审查和回归结果作为发布证据。

## 框架与前端评价

优点：API、资源、文档、运行时、技能治理、存储仓库、前端视图有明确的模块边界；已有真实工具实现和大量回归用例；前端具备上传、会话、执行轨迹、审批和产物下载的基础流程。

不足：通用运行时和业务图两条执行路径需要持续统一身份、权限、持久化和错误语义；`orchestrator.py` 和 `tool_handlers.py` 较大，解释性注释及增量编号较多，维护成本偏高；运行记录、事件和技能的部分状态仍进程内保存；静态展示和大量测试不能代替真实模型、真实连接器、负载与恢复验收。

前端生产构建和 lint 已验证，但构建仍有大于 500 KB 的分块提示。没有在本次完成整体视觉设计评审、完整浏览器矩阵、可访问性审核或大规模交互重构，不能仅凭构建通过称其“优秀”。

Makefile 的 lint/typecheck 通过只覆盖其声明的受管代码范围。本次 lint 债务检查仍为 460 项，与原有基线相同；这表示没有增加被追踪的债务，不表示全仓库已经没有静态检查问题。`check-full` 汇总后端门禁、债务检查和前端 lint/build，真实模型与集群验收仍需另行执行。

## 仍需完成的企业级验收

1. 持久化任务队列、执行租约、心跳及崩溃接管；跨工作进程的停止控制与事件流。完成前保持单 API 进程。
2. 技能演化/发布的数据库事务与唯一操作标识、并发发布验收和真实业务 Golden 集。
3. 上传入口的整体请求限制、压缩包解压配额、恶意文件扫描、解析时间/内存隔离；本次读取上限不等于全部上传和解析风险已消除。
4. 服务端显式本地路径输入的租户级允许目录策略。资源 ID 隔离已修复，但这不构成对整个文件访问平面的完整安全审计。
5. 真实 PostgreSQL/Ollama/外部连接器验收、断网与故障注入、备份恢复、容量与长时间运行测试。
6. 复杂文档视觉保真与破损文件专项语料；严格区分“内容修改”“格式调整”“损坏文件恢复”。
