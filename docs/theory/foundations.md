# ForgeFlow 理论地基

本文是 ForgeFlow 的理论底座，不是功能清单：每一节先说一条
大厂开源项目里被验证过的原理，再说 ForgeFlow 现在落到了
哪一步、哪一步还没落到。凡是写“未实现”的，都是真的未实现，
不要在简历、README 或对外介绍里把它说成已实现。

证据口径：调研里只有 3 页是 2026-10-29 直接读过的
（LangGraph 中断、OpenAI Agents SDK 交接、Google ADK
层级博客），其余结论来自搜索索引片段，未逐页复读，
引用时要按这个口径说。完整对比与来源见理论地基页
《ForgeFlow Theory Foundations》。

## 1. 路由与拓扑：中心路由 vs 对等交接 vs 图层扇出

- **Supervisor（中心路由）**：一个中心智能体用结构化路由
  决策选下一个工作者，所有工作者回到中心。优点是单条
  审计链、路由可复查；代价是每跳多一次模型调用。
  ForgeFlow 现状：`forgeflow/graph/builder.py` 的
  StateGraph 就是 hub-and-spoke，`SupervisorAgent` 只发
  `RoutingDecision`、不直接调工具，`forgeflow/graph/edges.py`
  做条件边。——已实现。
- **Swarm（对等交接）**：工作者之间直接交接，路由分散、
  延迟更低，但没有单一审计中心。ForgeFlow 没有 swarm，
  不要说成有。
- **图层扇出**：用 Send + 归约做并行分支，分支完成顺序
  不保证。ForgeFlow 的并行只在委派层
  （`forgeflow/runtime/delegation.py::delegate_parallel`，
  2–4 个只读专家，失败隔离），图层没有扇出。——未实现。
- **确定性 vs 意图路由**：代码条件边、Command、Send 是
  确定性的；模型按工具描述选目标是概率性的，必须用
  路由数据集度量。ForgeFlow 的 Supervisor 提示里目前只有
  stage / score / approval 状态，没有任务意图文本，所以
  `tests/data/supervisor_routing_cases.json`（60 例）度量
  的是“阶段驱动路由”，不是意图分类准确率。确定性基线
  60/60 只是规格一致性，LLM 模式 36/60 也只是该脚本
  提示下的分数，不是业务路由准确率。

## 2. 状态、检查点与人工审批

- **检查点是线程作用域**：`thread_id + checkpoint_id`，
  PostgresSaver / MemorySaver 只是后端。ForgeFlow：
  `forgeflow/graph/checkpointer.py`，Postgres 用
  AsyncPostgresSaver，离线用 InMemorySaver（仅进程内可续跑）。
- **中断的硬约束**：中断保存状态、可无限期等待、必须在
  同一线程 ID 上恢复；恢复时节点从头重跑，所以中断前
  的副作用必须幂等。ForgeFlow：`human_approval` 是
  `interrupt_before` 节点，`/approvals/{token}/approve` 续跑。
  ——已实现，但“中断前副作用幂等”要逐个工具复查，不能
  默认成立。
- **审批要落在具体物上**：批的应该是待定的某一次工具
  调用或某一份 diff，而不是一句“同意继续”。ForgeFlow
  的代码提交审批（`forgeflow/codeplane/approval.py`）
  是 diff 绑定的；调研结论是：没有任何 surveyed 框架
  自带 diff 哈希校验的审批，ForgeFlow 的
  `HandoffPayload.diff.sha256`（`runtime/handoff_payload.py`）
  是应用层自己补的，审批门校验时必须比对该哈希，
  不能只看模型自报的 diff。

## 3. 传递与边界：上下文、工具、产物是三条通道

OpenAI Agents SDK 的教训是三条通道不能混用：

- 应用状态（不进模型）放租户、审批策略；
- 交接元数据（模型可决定的小量信息）不决定目标、
  不替代主输入；
- 主输入默认是完整历史，过滤工具不做脱敏，复制进
  下一智能体的内容也不会被过滤掉。

ForgeFlow 的对应做法：

- 租户/审批策略在平台上下文，不进模型提示（见
  `docs/quality/prior-context-injection-fix-2026-10-29.md`）。
- 前序内容（parent run 意图、结论、产物、diff）现在走
  单独的 user 块并按节消毒，不再拼进系统提示；RAG
  检索节也是按节消毒，一节高危不再连累全部文档。
- 跨项目交接不走模型复述：新任务只写
  `handoff_from_run_id`，服务端从存储的源运行派生
  `HandoffPayload`（产物按引用 + sha256、状态显式、
  diff 由服务端算），见 `docs/quality/cross-project-handoff-upgrade-2026-10-29.md`。
- ADK 的产物模型值得继续学：产物带版本、只在加载时
  占 token、按 `(app, user, session)` 作用域隔离。
  ForgeFlow 的产物引用已有 `artifact_id + content_ref +
  sha256`，但版本化语义（同一产物多版本、旧版本可回查）
  还没有完整落地。——部分实现。

## 4. 记忆：三类记忆 + 预算，不是“无限上下文”

- **三类**：情景记忆（某次运行发生了什么）、语义记忆
  （长期事实/偏好）、程序记忆（怎么做事的规则/技能）。
  跨线程记忆靠命名空间（user_id）而不是线程 ID。
- **去重是写时的工作**：Mem0 模式是先抽取、再对最相似
  的旧记忆做 ADD / UPDATE / DELETE / NOOP，而不是无脑
  追加。ForgeFlow：`forgeflow/memory/memory_manager.py`
  的 recall + `forgeflow/context/openviking.py` 的统一召回
  （记忆/技能/任务经验，去重、排序、预算）已有，但
  “写时去重与冲突裁决”的完整规则没有像 Mem0 那样
  形式化。——部分实现。
- **预算在每个边界上**：上下文压缩器（如 OpenHands 的
  condenser：头 + 摘要 + 尾，完整日志保留）不是记忆库。
  ForgeFlow 的上下文预算、技能成对实测 token 变化
  （本地 Ollama qwen3:8b，63,955 → 44,904，-29.8%）
  是实测数，只能用在它自己的实验条件下，不能推广成
  通用节 token 比例。

## 5. 技能：打包、版本、评估、回滚四件事分开算

- **打包**：SKILL.md 文件夹 + 元数据（名称、描述、
  何时用、何时不用），渐进披露（元数据约 100 token、
  正文 <5000、脚本只出结果）。ForgeFlow 的技能系统
  （指令打包、试运行、版本/回滚、关键词+向量 RRF 检索、
  评估后发布）在 `forgeflow/skills/` 已有完整实现链。
- **版本没有统一协议**：元数据里的 version 是自由文本，
  真实版本是 Git 提交 SHA、插件版本或 Skills API 版本；
  没有语义版本、弃用、迁移协议。ForgeFlow 的技能版本
  同样不要宣称“遵循 semver”，除非真的落了那套规则。
- **回滚不等于时光倒流**：重新钉住旧版本可以恢复技能
  本身，但已经写进的记忆和产物不会跟着回滚。
  ForgeFlow 的 `auto_rollback.py`、`versioning.py` 要按
  这个边界写测试和文档，不能让用户以为回滚能撤销一切。

## 6. 安全：数据与指令的边界是第一性原理

- **工具输出永远是数据，不是操作指令**。第二阶注入
  （工具结果里藏指令）不能只靠提示词挡，要靠代码层：
  最小权限、沙箱、人工审批、工具参数校验。
  ForgeFlow：工具输出包 `UNTRUSTED_TOOL_OUTPUT`、
  `forgeflow/security/`（注入检测、PII 脱敏、SSRF 守卫、
  工具输出守卫）、前序内容移出系统提示，都是这一层。
  ——已实现，但“提示词不能单独保证防注入”这句话要
  一直保留，不能因为加了标注就声称防注入已证明。
- **最小权限 + 类型化工具**：不要给模型裸 shell；
  代码执行只在 Docker 容器里（`CODEPLANE_TRANSPORT=docker`，
  只挂载目标项目），非 Docker 传输的交接代码任务直接
  拒绝，且拒绝文案要告诉用户设 docker，而不是悄悄放宽。
  ——已实现（见 `docs/codeplane-docker.md`）。
- **致命三联**：私有数据 + 不可信内容 + 对外出口同时
  出现时必须阻断或隔离。ForgeFlow 的 SSRF 守卫、租户
  隔离（Postgres RLS、运行/迁移分账号）是这一层的
  实现，但租户隔离是应用层选的命名空间策略，不是
  框架自带保证——跨租户的每一处查询都要有谓词，
  事件日志的租户谓词（审计 #4）仍是已知未修项。
- **A2A 不是信任**：Agent Card、任务生命周期、产物
  （不是消息）是信封，不是信任背书。ForgeFlow 的
  `forgeflow/a2a/` 是接口层，信任、租户、幂等仍是
  调用方自己的事。

## 7. 评估：黄金集、评判模型、防泄漏各管一摊

- **黄金集要从真实失败里来**，分层 + 对抗样本，
  确定性检查 + 评判模型 + 人工三层，CI 里做回归门
  （相对基线 + 成本/延迟预算）。ForgeFlow：
  `forgeflow/evaluation/`（黄金注册、回归、评判、
  防泄漏）+ 监督路由数据集是这条路的起点。
- **评判模型有偏见**（位置、自恋、啰嗦偏好），必须
  用人工标定校准，不能只看评判分数。
- **防泄漏**：数据集版本化与血缘、留出集绝不用于调参、
  检索和缓存两层都要做租户过滤。ForgeFlow 的
  `leakage_guard.py` 是这层的实现，留出集的使用纪律
  要写进评估 SOP，不能只靠代码。
- **路由数据集能证明什么、不能证明什么**（见第 1 节）：
  能证明在该数据集上与标注者的一致性、混淆分布、
  回归；不能证明真实意图、域外表现、下游任务成功、
  小差异的类别优越性（在方差内）、漂移下的稳定性。

## 8. 失败理论：先分类，再谈重试

- **先分类**：瞬时 / 卡住 / 格式错误 / 语义错误 /
  状态错误 / 预算耗尽。不同类用不同策略，不能一律重试。
- **幂等与“未知”态**：重试前先凭回执对账，区分
  “失败”和“结果未知”。ForgeFlow 已落地的例子：
  同一运行内 `code.execute` 成功后重试直接复用
  （`reused=True`，不建新容器、不扣预算），最终
  组装优先取成功执行而非最后一次降级执行。
  ——同一运行内已实现；跨运行的认领表
  `UNIQUE(source_run_id, target_project_id, kind)` 还没有
  持久层迁移。——未实现。
- **预算与熔断**：每调用、每步、每 token、墙钟都要有
  上限；按依赖做熔断，熔断要以类型化结果返回，
  不能悄悄降级成成功。ForgeFlow 的委派预算上限 4、
  模型调用上限、代码执行预算是这层的实现；
  通用熔断器框架没有自带。——部分实现。
- **降级要贴标签**：降级结果必须写明缺了什么；
  部分扇出要收集成功分支、标记超时分支，关键分支
  失败时按“继续 / 重试该分支 / 直接失败”显式决策，
  不能把部分说成完整。ForgeFlow 的 `HandoffPayload`
  状态（completed / partial / failed）+ `missing` 清单
  就是这条规则在交接上的落地。

## 9. 15 条可复用原则（落到 ForgeFlow 的检查表）

1. 服务端按 ID 解析，绝不让模型复述结果。
2. 载荷类型化、服务端校验，哈希不符就拒绝，不降级。
3. 产物按引用传，内联只是工作副本。
4. 前序内容标为不可信数据，放单独状态键。
5. 租户与审批策略不进模型上下文。
6. 提交工具只挂在审批通过后的节点上。
7. diff 由服务端算，审批比对服务端哈希。
8. 中断前副作用幂等，恢复从头重跑也不怕。
9. 交接先认领再执行，重复请求返回已有运行。
10. 部分只能检查，失败只传错误，完整才能进提交门。
11. 目标工作区白名单化，每运行全新容器、只挂目标项目。
12. 每次交接一条结构化审计记录。
13. 记忆写时去重，检索与缓存两层租户过滤。
14. 技能回滚只回滚技能，不撤销已写记忆与产物。
15. 降级、部分、未知三种状态都要显式，绝不混成成功。

其中 9、11 的持久层部分（认领表、Postgres 检查点
持久化、A2A 线上协议）尚未实现，见第 8 节。

## 10. 框架不提供什么（不要再从框架说明书里找）

| 能力 | LangGraph | OpenAI SDK | ADK | ForgeFlow 现状 |
|---|---|---|---|---|
| 跨运行跨租户交接 | 无 | 无 | 无 | 应用层自建（HandoffPayload） |
| 内置租户隔离 | 无 | 无 | 无 | 应用层命名空间 + RLS |
| diff 哈希审批 | 无 | 无 | 无 | 应用层自建（待审批门比对） |
| 熔断器 | 无 | 无 | 无 | 预算上限部分实现 |
| 技能 semver | 无 | 无 | 无 | 无，不要宣称 |
| Swarm 对等交接 | 有 | 无 | 无 | 无 |
| 图层扇出 Send | 有 | 无 | 无 | 无（仅委派层并行） |
| 崩溃后检查点续跑 | 有 | 无（仅 RunState JSON） | 有（会话/产物） | Postgres 检查点有，InMemory 仅进程内 |

## 11. 开放问题（下次调研要先回答的）

1. LangGraph 递归上限默认值随语言/版本而变，需按
   实际版本确认，不能写死。
2. CrewAI 长期记忆“只存评估不存输出”的说法只有单
   个二手来源，需复核。
3. ADK 2.0 图工作流是 beta 且只有二手来源，需复核。
4. Mem0 图分布的说法存在矛盾，需复核。
5. 厂商自测的基准数字、Claude Code 的硬编码规则与
   hook 优先级只有二手来源，不能直接引用为定论。
6. ForgeFlow 自己的开放项：事件日志租户谓词（审计 #4）、
   产物级 follow-up 消费（审计 #5）、测试命令 shell
   处理（审计 #7）、运行详情绝对路径（审计 #9，低）、
   认领表持久化、产物版本化语义、记忆写时去重规则
   形式化、意图感知路由（Supervisor 提示加入任务意图
   摘要后重测数据集）。
