## 二、仍真实存在的缺口（1 条，**已修**）—— **F-135**

### 现象

`GET /metrics/` **源层有、API 面无** `source_detail`（R5 §四 D5 判 **FAIL**，本轮独立复核确认仍存在）。

- 源层：`observability/metrics_source.py` 的 `summary()` **确实返回** `source_detail` ∈ {`hub_runs`, `workspace_runs`, `workflow_runs`}；
- API 面：`api/routers/metrics.py::get_metrics_summary` 用 `MetricsSummaryResponse(**payload)` 包装，
  而 `api/schemas.py::MetricsSummaryResponse` **未声明** 该字段 ⇒ **pydantic v2**（默认 `extra="ignore"`）**静默丢弃**；
- 后果：任务书要求 `GET /metrics/` 的响应对 hub 路径给出 `source_detail == "workspace_runs"` **未达成**；
  且 realstack 只在**源层**断言 ⇒ 源层 PASS **推不出** API 层 PASS（典型「假绿接缝」）。

### 修复（加性）

- `forgeflow/api/schemas.py::MetricsSummaryResponse` 新增 `source_detail: str = ""`；
  默认 `""` = **未报告**，绝不编造表名；`source` 保持历史值（`"postgres"` / `"hub_runs"`）以向后兼容。
- 新增 **API 面**钉子 `tests/unit/test_gapfix_f135_metrics_source_detail.py`（4 例）。

### 证据

1. **根因探针**（`_gap_probe_f135.py` → `_gap_f135_probe.json`）
   - 修复前：`declares_source_detail = false`；输入 `source_detail="workspace_runs"` ⇒ `dumped_source_detail = "<<DROPPED>>"`、`survives = false`。
   - 修复后：`declares_source_detail = true`；`dumped_source_detail = "workspace_runs"`、`survives = true`（源层同时给出 `hub_runs`）。
2. **junit 四列**（自读 XML）
   - 新测试 + 相关 metrics 回归（`test_gapfix_f135_*` + `test_hub_metrics` + `test_metrics_source` + `test_inc41_metrics_workspace`）：**24 / 0 / 0 / 0**。
   - **全量 `tests/unit tests/integration`**：`tests=3133 passed=3131 failed=0 errors=0 skipped=2`（1 skipped + 1 xfailed）。
3. **反事实（真跑，三层护栏）**（`_gapfix_f135_counterfactual.py` → `_gapfix_f135_counterfactual_out.txt`）
   摘掉 `MetricsSummaryResponse.source_detail` 字段 ⇒ 4 例**整组转红**（junit `tests=4 passed=0 failed=4`、rc=1）；
   复原 **sha256 逐字节一致**（`5ef54864740c6f32…958ba`）；复跑转绿 4/4 ⇒ **OVERALL PASS**；`job_assigned`、内存地板未触发。
